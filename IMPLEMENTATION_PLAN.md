# Argand — план реализации

Фокус этого плана — базовая функциональность: **отображение, редактирование и рисование спектра** (требования 1–5). Плагины/воркер (требование 6) спроектированы и вынесены в конец как отложенный трек.

Стек и архитектура — см. `CLAUDE.md`. Каждая фаза заканчивается проверяемым критерием «Готово, когда».

## Статус: что уже сделано через CLI

Перед GUI собран CLI `aspec` (`crates/cli`, бинарник `aspec`) — он рендерит
спектрограмму и усреднённый спектр сигнала в PNG. Он написан не как песочница,
а как затравка рабочего workspace: вся логика лежит в `argand-core`,
`argand-io` и `argand-dsp`, и GUI заберёт их без изменений. Подробности — в
`README.md`.

Тем самым закрыты:

- **Phase 1** — `Signal`/`SignalMeta`, `SampleType`, трейт `SampleSource`,
  `FormatReader`-слой в `argand-io`: WAV (uint8 / int16 / int32 / float32 /
  ненормированный float «CoolEdit 16x8»), FLAC, raw. Контейнер определяется по
  содержимому, а не по расширению. mmap + ленивое чтение, уже пройденные
  страницы возвращаются ядру: получасовой захват 172 МБ рендерится за ~0.8 с,
  RSS держится около 60 МБ и не растёт с длиной участка.
- **Phase 3** — STFT с настраиваемыми размером FFT, окном и перекрытием,
  свёртка кадров в колонки картинки на лету (память по размеру вывода, а не по
  длине файла), шесть цветовых схем, прогресс через коллбэк.
- **Phase 4** — двусторонний спектр `−Fs/2 … +Fs/2` с `fftshift` для complex и
  односторонний для real; ось в реальных Гц через `center_frequency`;
  полношкальный тон читается как 0 dBFS в обоих случаях.

Не сделано и остаётся за GUI: осциллограмма и min/max-пирамида (Phase 2),
редактирование (Phase 5), окно детального спектра (Phase 6), само окно и
конфиг (Phase 0). Крейты `argand-edit` и `argand-app` ещё не заведены,
GPUI в дерево не подключён.

Зависимости фиксируются в `Cargo.lock`. `vendor/` в git не хранится; для
локальной offline-сборки зависимости заранее загружаются через `cargo fetch
--locked` либо выгружаются в `vendor/` командой `./vendor-update.sh sync`.

## Phase 0 — Скаффолд и оболочка
Цель: пустое окно GPUI запускается на трёх ОС, конфиг читается.
- Cargo workspace с крейтами из `CLAUDE.md` (пока пустые каркасы).
- `argand`: окно gpui + gpui-component, базовая тема, dock-каркас (места под осциллограмму / спектрограмму / панель).
- Созранение состояния окна (размер, положение) между сессиями.
- GPUI и gpui-component на фиксированной git-ревизии.
- Загрузка `argand.toml` (serde + TOML), tracing-логи.
- CI-сборка под linux/windows/macos.

**Готово, когда:** `cargo run -p argand` открывает окно на всех трёх ОС (тестируемся только на native-OS для текущей машины); холодный старт субсекундный; конфиг применяется.

## Phase 1 — Модель данных и загрузка файла
Цель: открыть файл и получить in-memory представление сигнала.
- `argand-core`: `Signal` (real/complex, `sample_rate`, `center_freq`, метаданные), `Selection`, единицы.
- `argand-io`: трейт `FormatReader` (probe / open / read → ленивый источник отсчётов); встроенный WAV-ридер (в т.ч. стерео-как-I/Q как временный путь для тестов); заглушка-ридер под нестандартный формат.
- mmap входного файла; ленивый разбор; без полной загрузки в RAM.
- Открытие файла из UI (диалог), отображение метаданных (Fs, длина, тип).

**Готово, когда:** WAV и тестовый I/Q-дамп открываются; в статусе видны Fs / длина / тип; память не растёт линейно с размером файла.

## Phase 2 — Осциллограмма
Цель: быстрый time-domain просмотр с зумом/панорамой.
- `argand-dsp`: построение min/max-пирамиды (peak-кэш) в фоне.
- `argand-core`: `WaveformEnvelope` как выход для рендера.
- `argand`: отрисовка огибающей через paths/quads GPUI; выбор LOD по зуму; зум/пан/скролл; ось времени.
- Для complex — одна дорожка (I, Q); заготовка под спектрограмму.

**Готово, когда:** многочасовой файл скроллится/зумится плавно; первый кадр появляется почти мгновенно (рисуем из пирамиды по мере готовности уровней).

## Phase 3 — Спектрограмма
Цель: time-frequency вид, прогрессивный и быстрый.
- `argand-dsp`: STFT (настраиваемые размер FFT, окно, перекрытие) → магнитуда в dB → маппинг в colormap → RGBA-тайлы.
- Прогрессивность: грубый STFT сразу, уточнение в фоне; кэш тайлов.
- `argand`: показ тайлов как `image` GPUI; зум/пан трансформами; **общая ось времени** с осциллограммой (linked).
- Переключение/совмещение осциллограмма ⇄ спектрограмма; живые настройки FFT, включая размер, тип окна, перекрытие, цветовая схема.

**Готово, когда:** спектрограмма строится прогрессивно без фриза UI; ось времени синхронна с осциллограммой; смена параметров FFT отзывчива.

## Phase 4 — Корректность I/Q
Цель: правильная работа с комплексными сигналами.
- Односторонний спектр −Fs/2 … +Fs/2 с `fftshift`
- Ось частот в реальных Гц по `center_frequency` + `sample_rate`.
- Открыть реальный I/Q-захват (interleaved f32) и проверить корректность спектра/полосы.

**Готово, когда:** на тестовом тоне с известной частотой пик стоит в правильном месте двустороннего спектра; шкала в Гц корректна; вещественный сигнал даёт односторонний спектр.

## Phase 5 — Выделение и редактирование
Цель: базовые правки в объёме ocenaudio.
- `argand-edit`: сегментный буфер (piece-table) поверх mmap-оригинала + вставленные буферы.
- Стек команд (undo/redo), буфер обмена сегментов.
- Операции: select (в т.ч. мультивыделение), cut, copy, paste, delete, trim/crop; для I/Q — I и Q вместе.
- Интеграция с видами: инвалидация пирамиды/тайлов только на затронутых участках.

**Готово, когда:** cut/paste на многочасовом файле — мгновенные; undo/redo стабильны; осциллограмма и спектрограмма корректно обновляются после правок.

## Phase 6 — Окно детального спектра
Цель: глубокий анализ выделенного участка.
- Отдельное окно (gpui multi-window), берёт текущее выделение.
- Высокоразрешающий FFT, усреднённый PSD (Welch), зумируемая детальная спектрограмма.
- Свой тулбар: размер FFT, тип окна, усреднение, динамический диапазон; маркеры и поиск пиков.

**Готово, когда:** по выделению открывается окно с детальным спектром и независимыми настройками; маркеры/поиск пиков работают; окно обновляется при смене выделения.

## Сквозные задачи
- **Рендер-шов:** следить, чтобы типы GPUI не протекали в ядро (см. `CLAUDE.md`).
- **Многопоточность:** DSP и построение кэшей — вне UI-потока.
- **Конфиг:** персист настроек вида/FFT между сессиями.
- **Тесты:** юнит-тесты на `argand-dsp` (корректность STFT/PSD/частотной шкалы) и `argand-edit` (сегментный буфер, undo/redo); golden-тест на расположение пика.

## Риски и смягчение
- GPUI — движущаяся мишень (git-пин; бэкенд Blade → wgpu). Смягчение: фиксировать ревизию, держать рендер-шов для заменяемости тулкита (egui + wgpu как запасной путь).
- Кастомный GPU-канвас в GPUI ограничен набором примитивов. Смягчение: спектрограмма — текстура, осциллограмма — paths/quads; если упрёмся в производительность плотной отрисовки — растеризовать осциллограмму в текстуру или переключить тулкит.
- Требуется реальный GPU. Учитывать для VM/headless-сценариев.

## Отложено — плагины и воркер (проектное решение, сейчас не реализуем)
Транспорт — отдельный **процесс-воркер** (один бинарник, режимы `run` / `serve` / `describe`), который сам делает `dlopen` C-ABI библиотек; весь небезопасный FFI и краши изолированы от GUI.

Разделение плоскостей: **управление** — кадрированные сообщения по stdio (команды/события/мелкие результаты); **объёмные данные** — воркер читает входной файл сам и пишет большой выход в файл или shared memory, а по каналу ходят только ссылки. Кольцевой буфер в shm — только для непрерывного realtime, не для пакетной обработки участка.

UI настроек строится **хостом** из JSON-схемы параметров, которую отдаёт плагин; GUI-код границу не пересекает. Три уровня контракта: форматы; обработка без визуализации (например, ресемплер); обработка с визуализацией (демод/декод → типизированные результаты в отдельном окне).

Открытые вопросы к моменту реализации:
- пакетная обработка по выделенному участку vs непрерывный поток в реальном времени;
- воркер читает вход сам vs GUI передаёт отсчёты;
- нужен ли shm-ring.
